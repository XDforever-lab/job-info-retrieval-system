### 2.1 数据加载（第 44-70 行）

```python
def load_segmented_data():
    df = pd.read_csv(SEGMENTED_CSV, encoding='utf-8-sig')
    cols = list(df.columns)
    desc_col = cols[-2]   # "职位描述_分词" 列
    title_col = cols[-1]  # "招聘岗位_分词" 列
    return df, desc_col, title_col

def load_stopwords():
    # 读取 965 个停用词（前期实验四产出），存入 Python set
    # set 的查找是 O(1)，后面判断"某个词是不是停用词"时非常快

def parse_segmented(seg_text):
    # 将 "负责/嵌入式/软件/开发" → ["负责", "嵌入式", "软件", "开发"]
    return [w.strip() for w in seg_text.split('/') if w.strip()]
```

**为什么这样做？**
- 分词结果存在 CSV 里，格式是"词1/词2/词3"，用 `/` 分隔。`parse_segmented` 就是把这个格式还原成词列表。
- 停用词用 Python `set` 存储，因为后面每次遇到一个词都要判断是不是停用词，set 查找 O(1) 比 list O(n) 快得多。

### 2.2 顺排文档检索（第 77-107 行）—— 对比基线

```python
def sequential_search(query_terms, doc_words_list):
    results = []
    for doc_id, words in doc_words_list:          # 遍历 5000 篇文档
        word_set = set(words)                       # 当前文档的词集合
        if all(term in word_set for term in query_terms):  # 所有查询词都出现？
            results.append(doc_id)                  # 匹配成功
    return results
```

**这是第 3 章"顺排文档检索"的直接实现**：读一篇文档 → 检查是否匹配 → 读下一篇。相当于一本 5000 页的书，要找"Python"这个词出现在哪几页，就一页一页翻。时间复杂度 O(N×L)。

**为什么先做这个？** 不是为了实际使用，而是作为性能基线——证明后面的倒排索引确实更快。课堂上讲"倒排索引比顺排快"，这个脚本用实际数据验证了这个结论。

### 2.3 倒排索引构建（第 114-178 行）—— 核心

```python
def build_inverted_index(df, desc_col, title_col, stopwords):
    lexicon = defaultdict(lambda: {'df': 0, 'postings': []})

    for idx, row in enumerate(df.iterrows()):
        doc_id = idx
        # 解析这条文档的职位描述 + 招聘岗位的分词结果
        desc_tokens = parse_segmented(row[desc_col])
        title_tokens = parse_segmented(row[title_col])
        all_tokens = desc_tokens + title_tokens

        # 对每个词，记录它在这篇文档中出现的所有位置
        token_positions = defaultdict(list)
        for pos, token in enumerate(all_tokens):
            if token in stopwords or len(token) < 2:
                continue                   # 跳过停用词和单字词
            token_positions[token].append(pos)

        # 更新词典和倒排列表
        for token, positions in token_positions.items():
            lexicon[token]['df'] += 1      # 文档频率 +1
            lexicon[token]['postings'].append(
                (doc_id, len(positions), positions)  # (文档ID, 词频, 出现位置列表)
            )
```

**数据结构解释**：

```
lexicon = {
    "Python": {
        "df": 48,                              # 有 48 篇文档包含"Python"
        "postings": [
            (34, 1, [138]),                    # doc_34 出现 1 次，在第 138 个位置
            (38, 1, [160]),                    # doc_38 出现 1 次，在第 160 个位置
            (97, 3, [38, 245, 412]),           # doc_97 出现 3 次，在 38/245/412 位置
            ...
        ]
    },
    "开发": {
        "df": 1317,                            # 有 1317 篇文档包含"开发"
        "postings": [...]
    },
    ...
}
```

**为什么记录位置？** 对应第 3 章"支持短语查询"。虽然当前系统只用到了词频 TF，但位置信息保留后可以扩展：比如搜"Python 开发"时，如果"Python"和"开发"在文档中的位置相邻（pos_Python=138, pos_开发=139），说明是紧密短语，可以给更高分。

**构建耗时**：5000 篇文档，0.9 秒完成，38,288 词条。

### 2.4 倒排检索（第 181-207 行）—— 布尔 AND 逻辑

```python
def benchmark_inverted(query_terms, lexicon):
    first_term = query_terms[0]
    if first_term not in lexicon:
        return []  # 第一个词就不存在，直接返回空

    # 取第一个词的倒排列表 → 转为 set
    doc_sets = [set(doc_id for doc_id, _, _ in lexicon[first_term]['postings'])]

    # 与其他词的倒排列表逐一取交集
    for term in query_terms[1:]:
        if term not in lexicon:
            return []
        doc_sets.append(set(doc_id for doc_id, _, _ in lexicon[term]['postings']))

    return list(set.intersection(*doc_sets))  # 所有查询词共同出现的文档
```

**对比顺排的效果**（实测数据）：

| 查询词 | 顺排耗时 | 倒排耗时 | 加速比 |
|--------|---------|---------|-------|
| Python 开发 | 18 ms | 0.5 ms | **33×** |
| 财务 审计 | 19 ms | 0.3 ms | **72×** |
| 电气 工程 | 19 ms | 0.5 ms | **39×** |

**为什么这么快？** 顺排要遍历 5000 篇 × 每篇几百个词。倒排只需要查两行的索引（"Python"→48 篇，"开发"→1317 篇），然后取交集——计算量从"遍历全文"变成"查表+集合运算"。

#### parse_query()（第 188-193 行）

```python
def parse_query(self, query_text):
    import jieba
    words = jieba.cut(query_text.strip())       # 分词
    return [w.strip() for w in words
            if len(w.strip()) >= 2              # 过滤单字
            and w.strip() not in self.stopwords] # 过滤停用词
```

**为什么用 Jieba 而不是 CRF？** CRF 是离线训练的高精度分词器，但加载模型要 2-3 秒。Jieba 有预编译缓存，启动快。对于仅 2-5 个词的短查询，Jieba 和 CRF 的分词差异微乎其微。

#### query_to_vector()（第 203-214 行）—— 对应第 2 章"文献-语词矩阵"

```python
def query_to_vector(self, query_terms):
    vec = np.zeros(len(self.feature_names))  # 32365 维零向量
    for term in query_terms:
        if term in self.term_to_col:
            col = self.term_to_col[term]     # 词 → 列号
            df = self.idf.get(term, 1)
            vec[col] = math.log(self.N / df)  # 查询词的 TF-IDF 权重
    vec /= np.linalg.norm(vec)               # L2 归一化
    return csr_matrix(vec)
```

查询被表示为一个 32365 维的稀疏向量。只有查询词对应的维度有非零值。"Python"→ 第 1234 维 = 4.65，"开发"→ 第 5678 维 = 1.33。

#### compute_cosine()（第 216-219 行）—— 对应第 2 章"余弦相似度"

```python
def compute_cosine(self, query_vec):
    # tfidf_matrix 已 L2 归一化，query_vec 也已归一化
    # 所以 点积 = 余弦相似度
    scores = self.tfidf_matrix.dot(query_vec.T).toarray().flatten()
    return scores  # 长度为 5000 的数组
```

一个稀疏矩阵乘法 `(5000×32365) × (32365×1) = (5000×1)`，耗时约 2ms。

#### apply_title_boost()（第 224-230 行）—— 标题加权

```python
def apply_title_boost(self, scores, query_terms):
    boosted = scores.copy()
    for term in query_terms:
        if term in self.title_index:
            for doc_id in self.title_index[term]:
                boosted[doc_id] *= 2.0   # 标题命中 → 权重翻倍
    return boosted
```

**为什么标题权重 ×2.0？** 参考实验四的创新点"处于新闻标题中的词汇赋予 2.0 权重加成"。在招聘场景中，如果用户搜"Python"，岗位名就叫"Python开发工程师"的显然比"运维工程师（职位描述里提了一句 Python）"更相关。

```python
def highlight_keywords(text, query_terms):
    # 1. HTML 转义：<>'"& → &lt; &gt; 防止 XSS 注入
    result = escape_html(text)

    # 2. 按词长度从长到短排序
    #    比如查询词是 ["Python", "Python开发"]，先替换长的"Python开发"，再替换短的"Python"
    #    否则短词先替换会破坏长词
    terms = sorted(set(query_terms), key=len, reverse=True)

    # 3. 逐个替换: Python → <mark class="highlight">Python</mark>
    for term in terms:
        pattern = re.compile(re.escape(term), re.IGNORECASE)
        result = pattern.sub(f'<mark class="highlight">{term}</mark>', result)

    return result
```

**关键设计**：先替换长词再替换短词。如果不这样做，"Python开发"会被拆成"<mark>Python</mark>开发"，后面的匹配就失效了。

## 七、为什么这样设计——关键决策说明

### 决策 1：用倒排索引做布尔检索 + TF-IDF 矩阵做 VSM 排序

**为什么两者都要？** 分工不同：
- **倒排索引**：快速定位"包含这些词的文档有哪些"（布尔检索，对应第 3 章）
- **TF-IDF 矩阵**：给文档打分排序（VSM 余弦相似度，对应第 2 章）

流程是"先用倒排把 5000 篇缩小到 50 篇候选，再用 TF-IDF 给这 50 篇打分排序"。这样既快（倒排 O(logN)）又准（VSM 考虑了权重）。

### 决策 2：服务端渲染而不是前后端分离

SPA（单页应用）需要 React/Vue + API 异步加载，对 5k 数据的小系统来说是过度设计。服务端渲染（Flask Jinja2 直接输出 HTML）代码简单、页面秒开、不需要处理跨域和状态管理。从打开浏览器到看到结果只需一次 HTTP 请求。

### 决策 3：标题权重 ×2.0

实验四的核心创新点是"标题词 2.0 加权"。在招聘场景中，岗位名称是最精准的摘要——搜"Python"时，"Python开发工程师"（标题命中）肯定比"运维工程师 - 要求熟悉Python脚本"（仅正文命中）更相关。权重翻倍确保标题命中的岗位排在最前面。

### 决策 4：查询分词用 Jieba 而不是 CRF

CRF 模型加载需要 2-3 秒且依赖 pycrfsuite，查询通常只有 2-5 个词，Jieba 和 CRF 对短文本的分词结果几乎一样。Jieba 有缓存机制，启动零延迟。这是在"准确性"和"响应速度"之间的合理取舍。

### 决策 5：评价时用多条测试查询覆盖不同场景

20 条查询设计覆盖了：单关键词、多关键词、行业限定、城市限定、薪资限定、复合条件。这样的设计确保了评测结果不是偶然的——有的检索系统对简单查询表现好但对复杂查询差，全面的测试集能暴露这种问题。对应第 5 章"检索性能评价的一般步骤"。
